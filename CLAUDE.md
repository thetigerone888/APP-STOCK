# CLAUDE.md

Guidance for Claude Code (and other AI assistants) working in this repository.

## What this app is

**FeedbackIQ** — a mobile-first customer feedback/survey app (Thai + English UI copy)
built from the **Manus WebDev Expo template**. Businesses create surveys, distribute
them (QR/link/in-app/email), collect responses, and view sentiment/NPS analytics.

Read `design.md` for the full product spec (screens, flows, brand colors) and
`todo.md` for the feature checklist (nearly everything is already implemented/checked off).

**Important architectural note:** although the repo ships a full backend (tRPC + Drizzle +
MySQL + Manus OAuth), the actual FeedbackIQ feature set (surveys, responses, analytics)
is currently implemented **entirely client-side** with Zustand + AsyncStorage
(`lib/store.ts`, `lib/seed-data.ts`, `lib/analytics.ts`). The backend/auth plumbing is
template boilerplate that isn't wired into the survey features yet. Don't assume survey
data goes through tRPC/the database unless you're the one adding that.

**Unrelated app in this repo:** `marbohub-pos/` (`index.html` + `api.php`) is a separate,
unrelated single-file POS/stock app — plain HTML/JS talking to a PHP file-backed API. It
shares no code, stack, or deployment target with FeedbackIQ (see `marbohub-pos/README.md`).
Don't assume changes to FeedbackIQ's `lib/`/`app/` affect it, or vice versa. See `DEPLOY.md`
for how each app is deployed.

## Tech stack

- **Expo (React Native + react-native-web)**, Expo Router (file-based routing), NativeWind
  (Tailwind for RN) for styling.
- **State**: Zustand stores persisted to `AsyncStorage`.
- **Backend** (present but not yet used by survey features): Express + tRPC v11 server,
  Drizzle ORM over MySQL/TiDB, Manus OAuth for auth.
- **Testing**: Vitest.
- Package manager: **pnpm** (`packageManager: pnpm@9.12.0`). Use `pnpm`, not `npm`/`yarn`.

### The `_core/` convention

Any `_core/` directory (`server/_core`, `lib/_core`, `shared/_core`) is **framework-level
code generated by the Manus template**. Avoid modifying it unless you are deliberately
extending platform infrastructure. Feature work belongs in the sibling files (e.g.
`server/routers.ts`, `server/db.ts`, `drizzle/schema.ts`, `lib/store.ts`).

## Development workflow

```bash
pnpm install            # install deps
pnpm dev                # run Metro (Expo web on :8081) + server (:3000) concurrently
pnpm dev:metro          # Expo web only
pnpm dev:server         # tRPC/Express server only (tsx watch)
pnpm check              # tsc --noEmit — run after any nontrivial change
pnpm lint               # expo lint (eslint-config-expo)
pnpm format             # prettier --write .
pnpm test               # vitest run
pnpm db:push            # drizzle-kit generate && drizzle-kit migrate (only if schema.ts changed)
pnpm android / pnpm ios  # native builds via Expo
```

There is no backend database configured by default for local dev — `getDb()` in
`server/db.ts` returns `null` when `DATABASE_URL` is unset, and callers are expected to
handle that (`if (!db) return [] / throw`).

## Conventions to follow

- **Import alias**: use `@/...` for repo-root-relative imports (e.g.
  `@/components/screen-container`, `@/lib/store`) and `@shared/...` for `shared/`. Configured
  in `tsconfig.json`.
- **Styling**: NativeWind/Tailwind className props where practical; theme colors come from
  `useColors()` (`hooks/use-colors.ts`) / `constants/theme.ts`, not hardcoded hex values, so
  light/dark mode stays consistent. Brand palette is documented in `design.md` (`#6366F1`
  indigo primary, `#10B981` emerald success, `#F59E0B` amber warning, `#EF4444` red error).
- **Domain types** live in `lib/types.ts` — extend these rather than inlining ad hoc shapes
  for survey/question/response/analytics data.
- **Zustand stores** (`lib/store.ts`) are the source of truth for surveys/responses; they
  persist to AsyncStorage under keys `feedbackiq-surveys` / `feedbackiq-responses`. Mutating
  helpers already exist (`addSurvey`, `updateSurvey`, `addResponse`, `updateResponseTags`,
  etc.) — prefer extending the store over reaching into AsyncStorage directly.
- **Sentiment/NPS logic** is centralized in `lib/analytics.ts` (keyword-based sentiment,
  `calculateNPS`, `computeAnalytics`, CSV/JSON export). Reuse these rather than duplicating
  scoring logic in components.
- **Screens** default to `headerShown: false` in the root `Stack` (see `app/_layout.tsx`);
  set a native header explicitly per-screen only when needed. Use `presentation:
  "fullScreenModal"` (not `"modal"`) for any full-screen/login-style overlay so iOS tab
  switching keeps working.
- **Backend routes**: if/when you wire real backend features, add tRPC procedures in
  `server/routers.ts` (using `publicProcedure`/`protectedProcedure` from `server/_core/trpc`),
  query helpers in `server/db.ts`, and tables in `drizzle/schema.ts`, then run `pnpm db:push`.
  Full patterns (auth, LLM, storage, image gen, pagination, optimistic updates, testing) are
  documented in `server/README.md` — read it before touching backend code.
- **Auth**: `protectedProcedure` throws `UNAUTHORIZED`; any frontend caller of a protected
  procedure must catch `error.data?.code === 'UNAUTHORIZED'` and redirect, per
  `server/README.md`.
- **Tests**: put Vitest specs in `tests/*.test.ts`; existing tests cover `lib/analytics.ts`
  and a (currently skipped) tRPC auth logout test used as a template for router tests.
- **Bilingual content**: UI copy and seed data mix Thai and English — preserve Thai strings
  exactly as given (don't "fix" or translate them) when editing nearby code.

## Things to avoid

- Don't edit files under any `_core/` directory unless explicitly extending framework
  infrastructure.
- Don't assume a live database/OAuth session in local dev — code must degrade gracefully
  when `DATABASE_URL`/OAuth env vars are absent (existing helpers already do this; follow
  the same `if (!db) ...` pattern).
- Don't hardcode colors — use the theme system so dark mode isn't broken.
- Don't introduce a second state-management approach for surveys/responses; extend the
  existing Zustand stores.

## Source of truth & keeping this file current

This file is a navigation aid, not the spec. When it and another doc disagree, the other
doc wins:

- `design.md` is authoritative for product/UX decisions (screens, flows, brand colors).
- `server/README.md` is authoritative for backend patterns (auth, DB, tRPC, LLM, storage).
- `todo.md` is authoritative for feature status.
- The code itself is always authoritative over any doc, including this one.

Update this file in the same PR whenever you change something it describes — e.g. wiring
survey/response features to the real backend (the "entirely client-side" note above would
need to change), adding/renaming top-level directories, or changing a workflow command.
Treat a stale "Important architectural note" as a bug.
